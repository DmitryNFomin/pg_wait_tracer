## 3. "Nothing can be lost" is false as stated
- Same-value write: fires (VERIFIED B:615-620). So "transitions" and "hits" differ by design; H4 compares them.
- Two writes in one trap: INFERRED (x86 data breakpoint traps after each writing instruction) cannot merge. But the timestamp is taken on handler entry, and entry cost is not constant (5.26 us at 190k fires/s, 14.23 us at 5k/s, HO:177-179): short intervals carry a rate-dependent bias no criterion measures.
- Context: the product's comments call it NMI (B:222, B:290, B:717); UNVERIFIED by me for either kernel. Updating an existing element in place needs no lock. INSERTING takes a bucket lock and a free-list slot: INFERRED the same class of failure as the ring reservation. Lightweight already inserts in the handler and counts failures (B:566-568). Rule: the handler never inserts; every record exists before the first trap.
- Map full: 1024 records (H:46); a failed insert means that backend records nothing at all (VERIFIED B:707-710). INFERRED: a stalled reader under connection churn leaves dead records holding slots.
- Shared vs per-CPU: shared is required and sufficient for one backend (VERIFIED B:102-105, B:524-526). The wakeup tracepoint needed for "runnable" runs on another CPU than the backend: new concurrency, no existing code, UNVERIFIED.
- Reader vs handler: a map read from user space copies the record with no lock. INFERRED torn read (total already added, since-when not yet moved) double-counts a whole interval in that second. The product already paid for this exact shape (VERIFIED B:880-894, "DB Time inflated by a whole wait"). It needs a hand-made sequence counter and retry; INFERRED no lock helper usable in this program type and no batch read on 4.18, so a set of (backend, query, event) entries can never be read as one consistent snapshot.
- Mis-timing by design: closed time is credited to the second in which it is READ. A 30 s reader stall yields one 30 s lump, not 30 seconds. Per-second charts are only as good as reader scheduling at saturation.
- Counters: 64-bit ns never wraps; a 32-bit count wraps in 6.3 h at 190k/s (INFERRED arithmetic from HO:178).
- Watchpoint not scheduled: INFERRED debug-register slots are reserved at open, so shortage (gdb, another perf user, 4 registers; the product takes one for the pointer, then one for the word: B:720, B:576) fails loudly at arming, not silently later. Not tested by the plan. Throttling: measured absent on 6.8 only (VERIFIED PE:23-41); EL8 not measured, and HO:181-185 says its negative controls were incomplete.
- Address: VERIFIED B:31-35: before PG 17 it is MyProc plus a per-build offset; the pointer is re-targeted in InitProcess, hence a second watchpoint (B:720-769). Arming is done from user space, so the time between InitProcess and enable is unobserved for EVERY new backend. Processes with no word cannot be traced at all.
- Exit and PID reuse: exit leaves the record for user space to delete (VERIFIED B:880-884); fork overwrites the record of a reused PID (VERIFIED B:787-792). INFERRED: totals not yet read are erased. exec does not apply.
## 4. Already-running backends
- The buffer objection does not survive, but only if the order is reversed: enable first, read after. INFERRED (enabling on a running task is a synchronous cross-CPU call): after the enable returns every write traps, and the handler finishes before the backend continues; a transition and its reverse have nowhere to hide.
- Exact race. Today's order: a write between the read and the enable (K:414-418) is never seen, so the state is stale for a whole interval. Reversed order: a trap between the enable and the read makes the read value post-trap, and a user-space seed written into the handler's record overwrites the handler's update (whole-value write, K:322).
- Simplest correct rule: after enable, user space never writes the handler's record. The record starts as "unknown". The one read goes, with the times just before and after it, into a separate write-once entry. The reader decides: no trap yet -> that value since enable; first trap later than the read -> that value until the first trap; otherwise that slice is "started before tracing". No re-read, no sweep, no global condition. It must be proven under a 100k/s writer across thousands of armings; H7 does not do that.

INFERRED cause: the id is set after parse and stays while idle; an interval opened when ClientRead ends carries the previous statement; several statements in one message give no trap between them.

Added per-trap cost is one more lookup, negligible against 5 us (INFERRED).

## 7. H1-H8: can each fail, and what lets it pass while the idea is wrong
- H1: already known true: lightweight ran on EL8 4.18 (VERIFIED T, el8 rows). It tests nothing new (wakeup tracepoint, large records, no-insert rule, reader consistency). Add those or drop it.
- H2: can fail, for the wrong reason. INFERRED a lock wait longer than deadlock_timeout is two or more Lock intervals, so "counts known from the script" is false and a correct handler is killed or the criterion gets edited. 1% of a 1 s sleep is 10 ms: a constant 5 ms error passes. Right truth: a small writer process that counts and timestamps its own writes on the same clock (one exists, HO:103), tolerance in absolute us per interval; for PostgreSQL, an independent count from a uprobe on WaitEventSetWait for a latch-only script.
- H3: an identity. If every nanosecond goes to exactly one bucket the sum equals wall time by construction; it passes with every transition misattributed. It only detects torn reads. Missing: a mutant (handler skips 1 update in 1000) that must turn H2 and H4 red, or the gate cannot fire.
- H4: the hit counter is NOT independent. INFERRED it is incremented in the same kernel call that runs the handler; it detects "handler skipped or failed", never "trap not delivered", "armed late" or "wrong address": both counts are then equally short and the test is green. The 30 s stall is nearly vacuous without a stream; the dangerous case is stall + churn (section 3), which no test combines.
- H5: the same mechanism already measured 0.84 on EL8 and 1.00 on Ubuntu (VERIFIED HV:16). Expect a KILL on EL8 unless the 0.84 is explained first. A total over backends hides opposite per-backend errors; make it per backend.
- H6: comparator is wrong. "Better than the product's exact mode" is won by removing uprobes, which `--skip-usdt` already does with the stream on. Add both as arms, and make the PoC arm carry every probe the product will need (command and query edges, wakeups), or the number is a floor, not a result. Throttled: see section 2.
- H7: "has no record" passes vacuously: the fork tracepoint creates the record (VERIFIED B:787-792). 1% of a 60 s wait is 600 ms and hides a race measured in us. Missing: unaccounted time per process (exit minus fork minus accounted), a fast writer under repeated arming, and PG 13.
- H8: undefined truth: pg_stat_statements has calls and times, not wait counts. pgbench sends one statement per message, the one case where a stale id is harmless; add a multi-statement message, a pipeline and a function. Run it FIRST, not last, and on EL8.

## 9. The three most likely ways this ends the same way
1. Cost: the trap is the cost. Stream-free accounting already exists and costs +17-20% CPU per transaction throttled and 20-28% throughput at saturation; attribution then needs uprobes and it is back to about half.
2. Attribution: per-query and command-scoped numbers either come from a read already proven stale or from uprobes; keyed maps bring back a loss path and two views that disagree.
3. The stream returns as source of truth for the event-only tabs and short windows, with drops; the PoC is green because it never tests them, and its gates (H3 identity, H4 shared counter, 1% tolerances) cannot go red.
Cheapest kill, no new code, about 30 minutes per box: existing binary, `--mode full --lightweight` against no tracer, select-only at `-R 8000`, three alternated runs each, PostgreSQL CPU per transaction. If it is again above +10% (it was +19.7% and +17.1% on 2026-11-17), H6 is a KILL no handler rewrite can avoid. Next cheapest: H8 on one backend with a multi-statement script.
