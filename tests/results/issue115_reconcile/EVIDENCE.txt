================================================================================
0. THE TWO TOOLING BUGS, AND WHAT THEY TOUCHED HERE
================================================================================

BUG 1 — xp_gate `--exclude-pid` was capped at 16 and silently ignored the rest.
  Exposed: only the M2 ("strict backend set") exact-tier rows, which are the
  only place this run passes a long exclude list. NOT exposed: the analysis
  window (derived with no excludes), the M1 exact rows (one exclude), every
  pg_stat_activity figure (pgsa_variants.py filters with a Python set), and
  every kernel/schedstat/tracepoint figure (`--pids`, not `--exclude-pid`).
  Of the six first-pass runs, only sat1 exceeded the cap: 33 excludes passed,
  17 silently ignored. The other five passed 1-7.
  MEASURED SIZE: the re-run scores every capture twice with the fixed binary,
  once with the full list and once with the list truncated to 16 (`CAP16`
  rows in sat*.txt / unsat*.txt), which reproduces the bug exactly on the
  same data. The difference is 0.00 pp on exact S, exact C and the sampled
  tier in all six runs, i.e. below the 0.1 pp print resolution. The pids that
  fell off the list are short-lived helper backends that carry no command
  markers and essentially no events.

BUG 2 — bpftrace reprints every populated map at exit, so END histograms were
  being concatenated and their counts doubled.
  NOT USED HERE. The fix lives in kernel_cpu_arbiter.py's `delays`
  subcommand, which does not exist in the version the first pass ran and
  which this harness never calls. This run's kernel figures come from
  `report` (/proc/<pid>/schedstat counter deltas), `sched` and `sampbias`,
  which read per-dump cumulative counters bracketing the window, not
  histograms; the only histogram in sched2.bt is @sdelay, which is printed
  for the record and never parsed. Independent confirmation that nothing was
  doubling: the tracepoint on-CPU total and the /proc schedstat on-CPU total
  agree to ~1 % in both passes (sat 115.65 s vs 114.41 s here; 116.93 s vs
  115.69 s in the first pass) — a doubled histogram would show as ~2x.

VERDICT: neither bug moved a reported figure. Section 1 differs from the
first pass by at most ~1.5 pp on the saturated rows, which is
machine-to-machine variation between two cx33 instances (the CAP16 control
above shows the exclude cap contributed 0.00 pp of it), and every
conclusion in section 3 is unchanged.

3. WHICH METHODOLOGICAL CHOICE EXPLAINS EACH PRIOR DISAGREEMENT
================================================================================

(a) Unsaturated control, 0.2 pp (inv-1) vs 5.3 pp (inv-2)
    WHICH EXACT-TIER VARIANT WAS QUOTED, plus run-to-run spread.
      exact S - V1 = 5.58 pp [5.25..6.14]   <- inv-2's 5.3 pp
      exact C - V1 = 1.85 pp [1.35..2.54]   <- inv-1's 0.2 pp
    The two figures differ by exactly the straddle correction (3.73 pp
    unsaturated). Neither investigation was wrong; inv-1 quoted the
    straddle-corrected estimator and inv-2 the one that ships. inv-1's 0.2 pp
    is nonetheless optimistic: the corrected estimator still sits 1.9 pp
    above the reference here, of which 1.25 pp is the reference's torn rows.
    Ruled out as causes, measured: the backend set (0.07 pp on the exact
    side, 0.00 pp on the reference side), the denominator/sample weighting
    (oracle_share.py reproduces V1 exactly), and the exclude-list cap
    (0.00 pp).

(b) Straddle rule, 3.4 pp saturated (inv-1) vs 0.9 sat / 3.7 unsat (inv-2)
    INV-2 IS RIGHT; INV-1 IS WRONG HERE, including on the sign.
      measured: -0.43 pp saturated, +3.73 pp unsaturated
      (first pass, other machine, other tools: -0.40 / +3.73 — identical)
    Unsaturated reproduces inv-2's 3.7 pp exactly. Saturated the correction
    is not merely small, it goes the other way: proportional overlap credits
    slightly MORE CPU than the majority rule. Sorting alone changes nothing
    (exact A == exact S in all twelve runs across both passes), so the
    "single-pass banked/anchor sweep" is not a second error. inv-1's 3.4 pp
    came from its earlier partial reimplementation (46.2 -> 42.8 %), not from
    a sorted proportional recompute, and it carried that figure into the
    decomposition where it absorbed error that belongs to the sampler bias.
    The straddle rule's size tracks commands per backend-second, which is why
    the low-concurrency case is the WORSE one: 3884 cmd/backend/s unsaturated
    vs 2164 saturated.

(c) Sampler bias, 6.4 pp (inv-1) vs 3.7 pp (inv-2)
    SAME MEASUREMENT, DIFFERENT UNITS. inv-2 measured it directly as pp of
    wall-clock "on a processor or runnable" and reported -3.41 pp; we
    measure -4.58 pp [-5.02..-4.18] the same way. Divided by the sampler's
    own non-idle fraction (71.1 %) that is -6.45 pp [-7.11..-5.88] of the CPU
    share of non-idle, which is the unit inv-1's decomposition used and where
    it wrote 6.4 pp. inv-2's "revised down to about 3.7 pp of non-idle" is a
    unit error: its own number, converted, is ~4.8-5.0 pp of non-idle, and on
    this machine it is 6.5. Independent check: the exact-vs-reference gap
    grows by 6.5 pp from unsaturated to saturated (1.85 -> 8.36), which is
    the sampler bias and nothing else.

(d) Torn reads, 3.4 % (inv-1) vs 0.47 % saturated (inv-2)
    DENOMINATOR AND REGIME. Torn = state='active' AND wait_event='ClientRead'.
      as % of ALL sampled rows:    0.58 % saturated, 2.17 % unsaturated
      as % of ACTIVE sampled rows: 0.89 % saturated, 3.17 % unsaturated
    inv-2's 0.47 % is % of all rows saturated (we get 0.58 %). inv-1's 3.4 %
    is the % of active rows in a low-concurrency window (we get 3.17 %).
    Both are right about their own quantity. The effect on the answer is
    small either way: correcting it moves the reference 0.56 pp saturated,
    1.25 pp unsaturated.

(e) The 23 % "non-active with no wait event" hole
    REAL AND THE BIGGEST SINGLE NUMBER IN THE TABLE, BUT IT LARGELY CANCELS.
    25.5 % of rows saturated, 11.8 % unsaturated. Counting them as CPU moves
    the reference by +17.7 pp saturated (37.9 -> 55.6). But that is the
    backend on a processor BETWEEN commands, and the exact tier discards the
    same time (74.8 s of CPU outside a command, saturated). Applied
    consistently to both sides the gap only narrows from 8.36 to 4.80 pp.
    It is a definitional hole in any "CPU share" built from pg_stat_activity,
    not the explanation of the exact-vs-sampled disagreement.

4. WHAT THE KERNEL SAYS
================================================================================
Saturated the backends spent 114.4 s executing and 107.0 s runnable-but-queued
against 112.7 s of PostgreSQL-reported wait. Run-queue delay carries no wait
event, so on the whole-backend definition the kernel's answer is 66.3 %. The
exact tier says 60.4 %, pg_stat_activity V2 says 55.6 %, V1 says 37.9 %.
Unsaturated: kernel 71.3 %, exact 67.2 %, V2 66.3 %, V1 60.3 %.
The exact tier is the closest of our instruments to kernel-observed execution
in every configuration and both regimes, on both machines and with both
versions of the tooling. #115's original conclusion stays inverted.
