3. WHICH METHODOLOGICAL CHOICE EXPLAINS EACH PRIOR DISAGREEMENT
================================================================================

(a) Unsaturated control, 0.2 pp (inv-1) vs 5.3 pp (inv-2)
    WHICH EXACT-TIER VARIANT WAS QUOTED, plus run-to-run spread.
      exact S - V1 = 5.54 pp [4.31..7.21]   <- inv-2's 5.3 pp
      exact C - V1 = 1.81 pp [0.51..3.41]   <- inv-1's 0.2 pp
    The two figures differ by exactly the straddle correction (3.73 pp
    unsaturated). Neither investigation was wrong; inv-1 quoted the
    straddle-corrected estimator and inv-2 the one that ships. The remaining
    spread is run-to-run: 3 pp peak-to-peak on a 39 s window.
    Ruled out as causes, measured: the backend set (0.00 pp), the
    denominator/sample weighting (oracle_share.py reproduces V1 exactly),
    and the sampler's own scheduling bias (-0.82 pp unsaturated).

(b) Straddle rule, 3.4 pp saturated (inv-1) vs 0.9 sat / 3.7 unsat (inv-2)
    INV-2 IS RIGHT; INV-1 IS WRONG HERE, including on the sign.
      measured: -0.40 pp saturated, +3.73 pp unsaturated.
    Unsaturated reproduces inv-2's 3.7 pp exactly. Saturated the correction
    is not merely small, it goes the other way: proportional overlap credits
    slightly MORE CPU than the majority rule. Sorting alone changes nothing
    (exact A == exact S in all six runs), so the "single-pass banked/anchor
    sweep" is not a second error. inv-1's 3.4 pp came from its earlier
    partial reimplementation (46.2 -> 42.8 %), not from a sorted proportional
    recompute, and it carried that figure into the decomposition where it
    absorbed 3.4 pp that in fact belongs to the sampler bias.
    The straddle rule's size tracks commands per backend-second, which is why
    the low-concurrency case is the WORSE one: 3832 cmd/backend/s unsaturated
    vs 2111 saturated.

(c) Sampler bias, 6.4 pp (inv-1) vs 3.7 pp (inv-2)
    SAME MEASUREMENT, DIFFERENT UNITS. inv-2 measured it directly as pp of
    wall-clock "on a processor or runnable" and reported -3.41 pp; we
    measure -4.75 pp [-5.15..-4.41] the same way. Divided by the sampler's
    own non-idle fraction (70.8 %) that is -6.71 pp [-7.23..-6.27] of the CPU
    share of non-idle, which is the unit inv-1's decomposition used and where
    it wrote 6.4 pp. inv-2's "revised down to about 3.7 pp of non-idle" is a
    unit error: its own number, converted, is ~4.8-5.0 pp of non-idle, and on
    this machine it is 6.7. Independent check: the exact-vs-reference gap
    grows by 6.9 pp from unsaturated to saturated (1.81 -> 8.70), which is
    the sampler bias and nothing else.

(d) Torn reads, 3.4 % (inv-1) vs 0.47 % saturated (inv-2)
    DENOMINATOR AND REGIME. Torn = state='active' AND wait_event='ClientRead'.
      as % of ALL sampled rows:    0.52 % saturated, 1.95 % unsaturated
      as % of ACTIVE sampled rows: 0.81 % saturated, 2.86 % unsaturated
    inv-2's 0.47 % is % of all rows saturated (we get 0.52 %). inv-1's 3.4 %
    is the % of active rows in a low-concurrency window (we get 2.86 %).
    Both are right about their own quantity. The effect on the answer is
    small either way: correcting it moves the reference 0.50 pp saturated,
    1.14 pp unsaturated.

(e) The 23 % "non-active with no wait event" hole
    REAL AND THE BIGGEST SINGLE NUMBER IN THE TABLE, BUT IT LARGELY CANCELS.
    25.9 % of rows saturated, 11.3 % unsaturated. Counting them as CPU moves
    the reference by +17.7 pp saturated (38.6 -> 56.3). But that is the
    backend on a processor BETWEEN commands, and the exact tier discards the
    same time (76.2 s of CPU outside a command, saturated). Applied
    consistently to both sides the gap only narrows from 8.70 to 5.11 pp.
    It is a definitional hole in any "CPU share" built from pg_stat_activity,
    not the explanation of the exact-vs-sampled disagreement.

4. WHAT THE KERNEL SAYS
================================================================================

against 110.0 s of PostgreSQL-reported wait. Run-queue delay carries no wait
event, so on the whole-backend definition the kernel's answer is 67.1 %. The

The exact tier is the closest of our instruments to kernel-observed execution
in every configuration and both regimes. #115's original conclusion stays
inverted, now with a spread rather than a single run behind it.
